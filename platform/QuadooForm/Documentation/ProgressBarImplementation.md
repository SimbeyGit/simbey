# ProgressBar implementation

`ProgressBar` is a native `msctls_progress32` control, registered through the
ordinary visual factory catalogue. Studio and the standalone designer discover
its descriptors and palette icon without a control-specific designer path.

The properties are signed 32-bit integers: `Min` (0), `Max` (100), `Position` (0),
and `Step` (10). The defaults and `StepIt()` follow
[TProgressBar's Step property](https://docwiki.embarcadero.com/Libraries/Florence/en/Vcl.ComCtrls.TProgressBar.Step)
and [StepIt method](https://docwiki.embarcadero.com/Libraries/Athens/en/Vcl.ComCtrls.TProgressBar.StepIt).
Position assignments clamp to the range. Range changes clamp Position before
observers are notified; observers can reenter or destroy the control safely.
Reversed ranges fail with E_INVALIDARG before making changes. Equal limits are
accepted. A zero Step does nothing; signed steps wrap past the range limits like
the native [PBM_STEPIT message](https://learn.microsoft.com/en-us/windows/win32/controls/pbm-stepit).
Wide intermediate arithmetic avoids overflow at the signed integer limits.

All four properties use the existing descriptor-driven storage and JSON format.
Explicit integer descriptor ranges now take precedence over the default generic
integer limits; this also permits parsing INT_MIN when JSON represents it as a
long integer. Descriptors without an explicit range retain their previous limits.
Definition loading validates the final range together, independently of JSON
property order, and clamps the initial Position. Logical values remain unchanged
at 96/144/192 DPI; the existing layout engine scales the HWND geometry.
ForeColor and BackColor retain their Quadoo Color values and are resolved when
passed to the native control, including system-color and theme changes.

Native code can query the additive `IQuadooProgressBar` capability (IID ending
004C) for Get/SetPosition, Get/SetMin, Get/SetMax, Get/SetStep, and StepIt. Existing
interface IIDs and vtables are unchanged. Scripts use ordinary component
properties and `ProgressBar1.StepIt()`; no compiler or VM changes are required.
The progress control does not join keyboard tab traversal. It inherits the
existing window lifecycle, layout, property notifications, and window events.

`Icons/ProgressBar.png` and `Icons/ProgressBar.ico` are generated by the existing
palette artwork generator. Both are 20x20; the ICO uses an uncompressed 32-bit
DIB and AND mask for XP compatibility. Resource 129 is embedded in QuadooForm.dll
and supplied through the same IQuadooPaletteIcon capability as other controls.

## Validation

Build affected individual projects, reusing existing dependency DLLs:

```bat
tests\platform\QuadooForm\build-application-lifetime.cmd Debug Win32
tests\platform\QuadooForm\build-application-lifetime.cmd Release Win32
```

That existing build helper covers the runtime, private tests, independent test
extension, native harness, shared designer, standalone designer, designer tests,
AQVMT, Studio, Studio integration tests, and application script tests. It does
not rebuild SimbeyCore.dll, JSON.dll, or the compiler/VM dependency DLLs.

Run the focused checks and full native/private regressions:

```powershell
& .\tests\platform\QuadooForm\test-progressbar.ps1 -Configuration All -Full
```

Focused tests cover defaults, public COM identity, 32-bit ranges, invalid range
rollback, clamping, positive/negative/zero steps, native wrap equivalence,
reentrant observers, destruction during notification, DPI, JSON round trips,
initial clamping, signed integer parsing, and factory lifetime. Designer tests
cover palette discovery, property inspector editing, persistence and reload.
Studio tests cover adding the control, generating its script member, saving,
and reopening. Application tests exercise the script properties and StepIt.
The existing palette suite also validates icon ownership, DPI, scrolling, and
resource lifetime with the additional factory.

The designer test host now explicitly shows itself after creation: a hidden
launcher can otherwise suppress the first WS_VISIBLE window and invalidate the
existing palette hit-testing tests.

Win32 Debug and Release builds and the test results are recorded in
`tests/results/ProgressBarLogs`. Validation uses the installed Windows host and VS2008;
an actual Windows XP VM run remains a manual compatibility check. No newer
progress APIs or messages were introduced.

Both Win32 configurations built without errors or warnings. Final results were
identical in Debug and Release:

| Suite | Assertions | Result |
| --- | ---: | --- |
| Focused native ProgressBar | 76 | Passed |
| Focused shared designer | 5 | Passed |
| Shared palette/icons/resources | 1,435 | Passed |
| Studio ProgressBar integration | 3 | Passed |
| Application script/runtime | 136 | Passed |
| Complete native harness | 9,617 | Passed |
| Complete private storage/metadata tests | 1,544 | Passed |

The complete native harness includes the focused native assertions. The native
wrap comparisons cover both directions, exact negative multiples, and steps
larger than the range. Runtime DLL, Studio executable, and AQVMT template retain
PE subsystem version 5.0. Changes are left uncommitted in Subversion.
