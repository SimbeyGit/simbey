# AQVMDbg implementation plan

Enable **Start Debugging (F5)** for Quadoo Studio Application projects. Use the existing WQVMDbg session model for breakpoints, stepping, call stacks, and variable inspection. Run the application with the same AQVM host and form lifetime rules as **Run Without Debugging**. Studio sends the compiled script, debug data, and form and frame definitions over the socket. AQVMDbg.exe stays a reusable executable whose resources are independent of the project.

This plan defines Stage 4B of the Application runtime work, including connection to manually started debuggers. Deployment and export remain separate from a debug session.

## 1. Share Application compilation and start an ordinary debugger session

- Extract the input preparation in `ApplicationTarget.cpp` from executable creation. Both Application commands should save the project, validate the saved script declarations and definitions, require exactly one Default form, and capture and verify the same input snapshot. Reuse `AQVM::GenerateStartup` and the same absolute include paths, source encodings, and project-specific virtual source tag. The generated startup remains in memory. It creates and shows the Default form, then enters `Host.RunApplication()` with the same lifetime rules as the regular application.
- Keep the existing WQVM debugger compilation path in `CStartDebuggerDlg`. Give Application projects a preparation branch that calls `QuadooParseTextToStream` with `QUADOO_COMPILE_LINE_NUMBER_MAP | QUADOO_COMPILE_FOR_DEBUGGING` and collects bytecode, the debug stream, and `IQuadooDebugTree`. Keep compiler diagnostics and the debug tree on the Studio UI side. Send the debug stream and existing breakpoints with the bytecode. Use the compiler's original source paths as debugger keys even when the target machine has a different filesystem.
- Finish compilation and form capture on the UI thread before starting the connection worker. Hand the worker owned byte streams and deployment inputs for the same snapshot. Keep startup cancellation in the existing dialog and display compiler errors before launching a debugger process.
- In `CQuadooProject`, route Application F5 through `CStartDebuggerDlg` and the existing `CQuadooDebugSession` and `AttachDebugger` paths. Enable the existing debugger commands according to session and breakpoint state. Leave the standalone Compile/export command on its current schedule.

## 2. Extend debugger startup for Application payloads

- Keep protocol version 2 and its existing startup sequence for QVMDbg and WQVMDbg. Give AQVMDbg a distinct Application startup revision in the `QDM_HELLO` frame. Keep the existing message envelope and message numbers, then append Application-specific IDs. Include target architecture in the Application handshake and require a matching Win32 or x64 host for this release. Have AQVMDbg confirm the handshake before Studio sends the project payload. An unexpected hello, early close, or startup timeout should identify the expected AQVMDbg protocol and architecture in the Studio error.
- Send the existing script path, script arguments, bytecode, debug data, and breakpoints, then send `QDM_APP_CATALOG`, one `QDM_APP_DEFINITION` per catalog entry, and `QDM_START`. Use the existing AQVM catalog schema for the Default class, unit kinds and IDs, event interface names, and module filenames. Encode the catalog and definitions as UTF-8 JSON. Prefix each definition with an explicit class-key length and key, and derive the remaining JSON length from the frame. Send every declared form and frame so the external class loader can create any unit on demand. Neither paths to the source definitions nor serialized debugger trees are needed on the target.
- Validate frame order, checked lengths, encodings, schema, the Default form, and one definition per declared class with the expected Form or Frame root type. Reject missing, extra, and duplicate definitions before executing code. Use the existing 64 MiB per-message debugger ceiling and the AQVM 32 MiB per-JSON-object limit. Cap the aggregate Application JSON payload at 128 MiB for this release and apply the same limits before sending and before receiving. Keep connect, handshake, transfer, and startup acknowledgement cancellable and bounded. Test fragmented frames and truncated connections using the same receive path as full frames.
- Have AQVMDbg send a startup result with an HRESULT and a short diagnostic on validation or bootstrap failure. On success, send the acknowledgement after native host and VM setup and before any script constructor or entry point can report a breakpoint. Keep that ordering explicit so the worker can consume the acknowledgement and hand the socket to the existing UI debugger without losing the first stop. Reuse the existing execution messages after that handoff. Report a pre-entry failure in Studio instead of reducing it to a socket-close error.

## 3. Build AQVMDbg around the AQVM runner

- Use the existing SVN-copied `AQVMDbg.vcproj`, entry point, and solution mappings. Keep WQVMDbg's entry flow and shared `CQuadooDebugHost` as the transport and execution-controller template. Replace AQVMDbg's copied `WQVMRun` binding with an AQVM runner and update its project sources, references, manifest, and link dependencies to match the AQVMT runtime. Build `AQVMDbg.exe` beside the matching Studio executable in all four solution configurations. Keep the WQVMDbg entry point and execution behavior intact.
- Extract a private runner from AQVMT's entry path that accepts a program identity, bytecode stream, optional debug stream and debugger, catalog, definition source, script arguments, and show command. AQVMT supplies its existing resource-backed inputs. AQVMDbg supplies the socket-backed inputs, uses `QVMCreateLoader` with the existing debugger, and registers bytecode with the debug stream. Keep Studio source identity separate from the debugger executable directory and the runtime working directory. Use the project arguments for AQVM's `WinMain` and script argument access, and keep debugger launch switches separate.
- Initialize common controls, DPI behavior, OLE, `CAQVMHost`, the real runtime component registry and `QuadooPlugin` factory, and the external class loader on the VM/GUI thread. Share AQVMT's VM construction, `WinMain` invocation, `Host.RunApplication()` message pump, and shutdown ordering. Keep the socket controller on its existing thread and all form creation and destruction on the VM/GUI thread. Report script breakpoint, exception, and inspection results through the shared debugger.
- Add a private definition lookup seam at `CApplicationRuntime::LoadDefinition`. AQVMT keeps its resource lookup. AQVMDbg owns an in-memory map indexed by the validated script class name, with key matching consistent with the existing AQVM catalog lookup. The receive side owns framed bytes until handoff. Parse the final catalog and map on the VM/GUI thread before execution and keep their entries read-only for the session. Preserve the existing per-instance definition cloning and `Form.Create(this)` and `Frame.Create(this, Owner)` behavior. Registering forms, event binding, and module resolution should use the same paths in both executables. No published QuadooForm or QuadooScript interface changes are expected.
- Reuse the existing Stop message and restrict the process wait and termination fallback to a locally launched child. A manually started session sends Stop and detaches the socket. Breaking into or waking AQVM while it is idle in a native message pump is outside this pass, including nested modal loops. Breakpoints in constructors and in handlers entered from the pump are in scope. A manually started target that is still idle after Studio detaches can finish when its windows close.

## 4. Deploy dependencies only for local auto-start

| Startup setting | Studio behavior |
| --- | --- |
| Automatically start debugger | Find the matching `AQVMDbg.exe` alongside Studio. Copy any missing required AQVM runtime DLLs and project module files beside it before launching. Pass `-loopback` and use the configured project start directory as the child process working directory. |
| Connect to a manually started debugger | Connect directly to the configured debugger host and port. Compile and send the same payload without checking a local AQVMDbg installation, copying files, or launching a process. The operator starts the matching debugger with its dependencies already installed and the intended working directory. |

- Reuse the Application module settings reader for the Studio process architecture, including the legacy flat array as x86. Reuse module path and basename validation and detect case-insensitive collisions with the runtime and debugger executable. The catalog sent to the target contains the deployed basenames. Studio's local module source paths stay local.
- Check the target before probing the source. An existing destination file satisfies the copy step, even when its contents differ or the configured source has moved. Copy an absent file from the normal runtime location or configured project module source. Publish with no replacement and handle a file appearing concurrently as an existing destination. If the destination is a directory or a required source is missing, report the dependency name and path. Keep this policy separate from non-debug Application output preparation.
- Update the shared `QuadooDebugHost.cpp` command-line parser to recognize `-loopback` as a flag alongside `-debug-port`. Bind the existing IPv4 listener to `INADDR_LOOPBACK` when the flag is present and to `INADDR_ANY` when it is absent. Add the flag in Studio's shared `CQuadooDebugSession::StartProcess` path so automatic launches of AQVMDbg, WQVMDbg, and QVMDbg all stay local. Keep the flag separate from the arguments delivered to the script. This listener change applies to all three debugger executables and uses the existing wire protocol.
- Document `AQVMDbg.exe -debug-port 1200` for manual remote startup and use the target machine's address in Studio's existing debugger host setting. Manual startup also accepts `-loopback` for a local-only session. The existing protocol accepts executable script from the connecting client, so document limiting the remotely reachable port to trusted debugger clients through the target firewall.

## 5. Integrate read-only mode and validate the workflow

- Lock Application script and designer mutation once the startup snapshot has been taken. Release the lock on startup failure, cancellation, Stop, disconnect, or normal exit. Apply it when switching or opening tabs and at the designer's mutation entry points, including inspector edits, keyboard and context commands, drag operations, and collection editors. Keep source navigation, breakpoints, call stack, variable inspection, designer selection, and inspection available. Save pending edits before taking the snapshot.
- Verify the ordinary flow in Studio. Start via F5, hit a breakpoint in a constructor, continue into a button or timer event, step through included scripts and frame handlers, inspect variables and call stacks, and add and remove breakpoints while the session is active. Verify read-only behavior and restoration across code and design tabs. Close the Default form with a secondary nonmodal form still open, then close the remaining form and verify normal debugger cleanup.
- Add focused transport and startup tests for legacy protocol compatibility, Application handshake and architecture mismatches, malformed or incomplete payloads, oversized frames and bundles, wrong root types, duplicate classes, cancellation, and first-breakpoint ordering. Verify local dependency copying with present, absent, and inaccessible files, preservation of existing files, and x86/x64 module selection. Test direct IPv4 connection to a manually started AQVMDbg on a second machine or VM with different paths and preinstalled dependencies. Verify that Studio auto-start still accepts loopback connections and rejects connections to the target's non-loopback address, including for QVMDbg and WQVMDbg. Verify that the executable hash and resources stay the same across debug launches and that no Application executable or generated startup file appears in the project.
- Build the existing Quadoo Studio solution in Win32 and x64 Debug and Release with the VS2008 toolset. Run the WQVMDbg and QVMDbg debugger smoke tests and an AQVMT non-debug Application smoke test. Validate the Application F5 flow on Windows XP with the Win32 build, including form creation, event breakpoints, and session exit. Preserve the repository's native containers, error handling, and source conventions.

## Running and testing

With **Automatically Start Debugger** enabled in Project Run Parameters, press **F5**. Studio launches the matching `AQVMDbg.exe` beside `QuadooStudio.exe`.

Breakpoints and variable inspection use the project compilation, including form and frame scripts. Dynamically loaded script modules run in their own VM instances and keep the project's debugger symbols intact.

For manual or remote startup, open the intended working directory on the target and launch the matching executable with `AQVMDbg.exe -debug-port 1200`. Install its runtime DLLs and project modules beside the debugger first. Set Studio's debugger host and port, turn off automatic startup, then press **F5**. The listener accepts direct IPv4 connections and runs the script it receives, so restrict the port to trusted debugger clients at the target firewall. Add `-loopback` for a manually started local-only session.

Run `QuadooStudioIntegrationTests.exe --application-debug-only` from the matching build output for the Application socket and F5 tests. Build the matching QVMDbg and WQVMDbg executables from the QuadooScript solution first for the legacy compatibility smoke tests in that command. Run `QuadooStudioIntegrationTests.exe --application-only` for the embedded AQVMT regression tests.
